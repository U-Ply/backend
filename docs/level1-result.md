### 3.1 관측 사항

동시 요청 30건 중 22건이 `PessimisticLockingFailureException`으로 종료됐다.
락을 걸지 않았음에도 DB 수준의 경합이 발생했으며, 원인은 JPA의 flush 순서다.

`save()` 호출은 즉시 SQL을 발행하지 않고 커밋 시점에
INSERT(`coupons`, `coupon_history`) → UPDATE(`campaign_stocks`) 순으로 실행된다.
각 트랜잭션이 인덱스 락을 보유한 상태로 마지막에 동일한 재고 행을 잠그려 하면서 교착이 발생한다.

이 실패는 락 대기 초과가 아니라 InnoDB가 즉시 검출한 교착이다.
`innodb_lock_wait_timeout`이 50초인데 테스트 전체가 0.123초에 종료됐으므로 대기 초과는 성립하지 않는다.

정상 종료된 8건 기준으로는 발급 수(8)와 재고 차감량(4)이 4건 어긋나,
동시성 제어가 없으면 재고 차감이 유실됨을 확인했다.

반복 측정에서 두 가지 규칙성을 확인했다.

첫째, 발급 수와 락 경합 실패의 합이 항상 정확히 30이다. 7회 관측 모두
8+22, 7+23, 6+24로 떨어졌다. 재고 소진·중복 발급·기타 예외가 전 회차 0건이므로
요청 30건이 빠짐없이 두 갈래로 분류됐고, 테스트 계획 5.4의 합계 검증을 매 회차 만족한다.

둘째, 실제 재고 차감량은 7회 내내 4로 고정이다. 발급 수는 6~8로 흔들리는데
`campaign_stocks`에 반영되는 차감량은 변하지 않았다. 정합성 위반 폭(2~4장)을 결정하는 것은
차감 쪽이 아니라 성공 응답 수의 변동이며, 위 flush 순서상 UPDATE 단계까지 살아남는
트랜잭션 수가 이 환경에서는 일정하다는 뜻이다.

동일 커밋(`5996522`)·동일 데이터베이스(`coupon_db_test`)에서 7회 반복 관측한 범위는 다음과 같다.

| --- | --- |
| 발급 수 | 6 ~ 8 |
| 재고 차감량 | 4 |
| 차이(유실) | 2 ~ 4 |
| 락 경합 실패 | 22 ~ 24 |

교착 발생 자체는 모든 실행에서 재현됐다.

run 1(`36cf2dc`, `coupon_db`)에서 관측한 범위는 발급 8~9, 재고 차감량 4, 차이 4~5,
락 경합 실패 21~22였다. 데이터베이스가 다르므로 두 회차의 범위를 하나로 합치지 않는다.
다만 발급 수가 6까지 내려가는 회차가 실제로 존재하므로, run 1의 범위는
NoLock의 변동폭을 실제보다 좁게 기록한 것이었다.

### 3.3 판정

기준선 목적을 달성했다.
테스트 계획 5.4의 NoLock 예외 규정에 따라 정합성 위반은 예상된 결과이며,
별도로 확인하는 항목은 다음과 같다.

- 전체 요청이 제한 시간 안에 종료됐다.
- 처리되지 않은 예외는 0건이다.
- 캠페인별 1인 1매 UNIQUE 제약이 동작했다.
- 요청 30건이 모두 집계됐다(합계 검증 통과).

run 1의 측정값과도 완전히 일치하므로, 이번 회차 범위에서 회귀는 없다.

### 4.1 판정

Level 1 공통 검증 항목을 모두 충족했다.

- 처리되지 않은 예외 0건
- 성공 건수(10) = 초기 재고(10)
- 쿠폰 수(10) = 성공 건수(10)
- 잔여 재고 0장 = 초기 재고 - 성공 건수
- 캠페인별 사용자 중복 발급 0건
- 요청 30건이 모두 집계됨(합계 검증 통과)
- 제한 시간 안에 전체 종료

### 4.2 락 timeout 관련

락 timeout은 0건이다.
모든 트랜잭션이 동일한 재고 행을 `SELECT ... FOR UPDATE`로 먼저 잠그기 때문에
획득 순서가 일정하며 교착이 성립하지 않는다.

현재 `GlobalExceptionHandler`는 `LOCK_TIMEOUT`을 503(SERVICE_UNAVAILABLE)으로 응답한다.
인수 기준이 5xx 0건이므로 Level 2·3에서 락 timeout이 발생하면 그대로 판정 실패로 이어진다.
Level 1 규모(재고 10 / 사용자 30)에서는 0건이지만, 대규모 부하에서의 발생 여부는 별도 확인이 필요하다.
