타임존은 락 획득 순서·교착 검출·스레드 스케줄링 중 어느 것에도 관여하지 않는다.
KST 환경과 UTC 환경에서 각각 반복 측정한 결과도 유의한 차이를 보이지 않았다(3.2 참고).

## 3. NoLock

동시 요청 30건에 대한 결과다.

| 항목 | 값 |
| --- | --- |
| 성공 응답 수 | 6 |
| 실제 쿠폰 수 | 6 |
| 실제 재고 차감량 | 4 |
| 차이(유실) | 2 |
| 초과 발급 | 0 |
| 재고 소진 응답 | 0 |
| 중복 발급 차단 | 0 |
| 락 경합 실패 | 24 |
| 기타 예외 | 0 |
| 동시성 테스트 실행 시간 | 0.131s |

성공 응답 수와 실제 쿠폰 수를 분리해 기록한다. 두 값은 개념이 다르다.
응답은 성공했는데 쿠폰이 남지 않는 경우가 생기면 그 차이 자체가 결함의 신호이기 때문이다.
초과 발급은 `실제 쿠폰 수 - 초기 재고`가 양수인 경우이며, 음수는 0으로 기록한다.

### 3.1 관측 사항

동시 요청 30건 중 24건이 `PessimisticLockingFailureException`으로 종료됐다.
락을 걸지 않았음에도 DB 수준의 경합이 발생했으며, 원인은 JPA의 flush 순서다.

`save()` 호출은 즉시 SQL을 발행하지 않고 커밋 시점에
INSERT(`coupons`, `coupon_history`) → UPDATE(`campaign_stocks`) 순으로 실행된다.
각 트랜잭션이 인덱스 락을 보유한 상태로 마지막에 동일한 재고 행을 잠그려 하면서 교착이 발생한다.

이 실패는 락 대기 초과가 아니라 InnoDB가 즉시 검출한 교착이다.
`innodb_lock_wait_timeout`이 50초인데 테스트 전체가 0.131초에 종료됐으므로 대기 초과는 성립하지 않는다.

정상 종료된 6건 기준으로는 쿠폰 수(6)와 재고 차감량(4)이 2건 어긋나,
동시성 제어가 없으면 재고 차감이 유실됨을 확인했다.

반복 측정에서 세 가지 규칙성을 확인했다.

첫째, 성공 응답 수와 락 경합 실패의 합이 항상 정확히 30이다. 전 회차가
6+24, 7+23, 8+22로 떨어졌다. 재고 소진·중복 발급·기타 예외가 전 회차 0건이므로
요청 30건이 빠짐없이 두 갈래로 분류됐고, 테스트 계획 5.4의 합계 검증을 매 회차 만족한다.

둘째, 성공 응답 수와 실제 쿠폰 수가 전 회차 일치했다. 락이 없어도 한 요청 안에서는
트랜잭션이 유지되므로, 응답만 성공하고 쿠폰이 남지 않는 경우는 발생하지 않는다.
NoLock이 잃는 것은 동시 요청에 대한 격리이지 한 요청 안의 원자성이 아니다.

셋째, 초과 발급은 전 회차 0건이다. Level 1 규모(재고 10 / 사용자 30)에서는 경합이
교착으로 먼저 걸러지기 때문에 초기 재고를 넘겨 발급되는 상황까지 가지 않는다.
이 규모에서 NoLock의 실패 양상은 초과 발급이 아니라 차감 유실 쪽이다.
Level 2에서 요청 20,000건을 던졌을 때 이 값이 0이 아니게 되는지가 V0 가설의 검증 지점이다.

첫째, run 2에 "재고 차감량은 4로 고정"이라고 기록했으나 표본이 부족한 판단이었다.

다만 발급 수(6~8)보다 변동폭이 작다는 관찰은 유지된다.

둘째, JVM 타임존 변경(KST → UTC)은 관측 분포를 바꾸지 않았다.
run 2와 run 3의 범위가 사실상 동일하다. 타임존은 락 획득 순서나 스케줄링에 관여하지 않으므로
예상과 일치하는 결과다. run 1의 범위가 좁게 기록된 것은 환경 차이가 아니라 표본 부족 때문이다.

run 3 코드에서는 요청당 쿼리가 2개 늘었다(`currentDatabaseTime`, `findCouponExpireAt`).
그럼에도 동시성 양상은 달라지지 않았다. 두 쿼리 모두 재고 행 락을 잡기 전에 실행되므로
직렬화 구간에 포함되지 않기 때문이다.

### 3.3 판정

기준선 목적을 달성했다.
테스트 계획 5.4의 NoLock 예외 규정에 따라 정합성 위반은 예상된 결과이며,
별도로 확인하는 항목은 다음과 같다.

- 전체 요청이 제한 시간 안에 종료됐다.
- 처리되지 않은 예외는 0건이다.
- 캠페인별 1인 1매 UNIQUE 제약이 동작했다.
- 요청 30건이 모두 집계됐다(합계 검증 통과).

5회 반복 실행에서 위 값이 모두 동일하게 재현됐다. 실행마다 값이 흔들리는 NoLock과 달리
비관적 락은 같은 재고 행을 `SELECT ... FOR UPDATE`로 직렬화하므로 결과가 결정적이다.
run 1·run 2의 측정값과도 완전히 일치한다. 그 사이 만료·발급 시각 산출 방식 변경,
JVM 타임존 UTC 고정, 요청당 쿼리 2개 추가가 있었으나 발급 정합성에는 영향이 없었다.

### 4.1 판정

Level 1 공통 검증 항목을 모두 충족했다.

- 처리되지 않은 예외 0건
- 성공 건수(10) = 초기 재고(10)
- 쿠폰 수(10) = 성공 건수(10)
- 잔여 재고 0장 = 초기 재고 - 성공 건수
- 캠페인별 사용자 중복 발급 0건
- 요청 30건이 모두 집계됨(합계 검증 통과)
- 제한 시간 안에 전체 종료

### 4.2 락 timeout 관련

락 timeout은 0건이다.
모든 트랜잭션이 동일한 재고 행을 `SELECT ... FOR UPDATE`로 먼저 잠그기 때문에
획득 순서가 일정하며 교착이 성립하지 않는다.

현재 `GlobalExceptionHandler`는 `LOCK_TIMEOUT`을 503(SERVICE_UNAVAILABLE)으로 응답한다.
인수 기준이 5xx 0건이므로 Level 2·3에서 락 timeout이 발생하면 그대로 판정 실패로 이어진다.
Level 1 규모(재고 10 / 사용자 30)에서는 0건이지만, 대규모 부하에서의 발생 여부는 별도 확인이 필요하다.

### 5.1 후속 확인 사항

- 초과 발급은 Level 1 규모에서 0건이다. V0 가설의 핵심인 초과 발급 발생 여부는
  Level 2(요청 20,000건)에서 별도로 판정한다.
- 만료된 캠페인에 대한 발급 요청은 현재 `IllegalStateException`으로 처리되어 500으로 응답한다.
  Level 2·3 인수 기준이 "기타 5xx 0건"이므로 도메인 오류 코드 추가가 필요하다. 별도 이슈로 진행한다.
- 요청당 쿼리 2개가 추가되어 Level 2의 TPS 비교 시 run 2 이전 수치와 직접 비교하지 않는다.
