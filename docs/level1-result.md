타임존은 락 획득 순서·교착 검출·스레드 스케줄링 중 어느 것에도 관여하지 않는다.

응답은 성공했는데 쿠폰이 남지 않는 경우가 생기면 그 차이 자체가 결함의 신호이기 때문이다.
초과 발급은 `실제 쿠폰 수 - 초기 재고`가 양수인 경우이며, 음수는 0으로 기록한다.

### 3.1 관측 사항

동시 요청 30건 중 24건이 `PessimisticLockingFailureException`으로 종료됐다.
락을 걸지 않았음에도 DB 수준의 경합이 발생했으며, 원인은 JPA의 flush 순서다.

`save()` 호출은 즉시 SQL을 발행하지 않고 커밋 시점에
INSERT(`coupons`, `coupon_history`) → UPDATE(`campaign_stocks`) 순으로 실행된다.
각 트랜잭션이 인덱스 락을 보유한 상태로 마지막에 동일한 재고 행을 잠그려 하면서 교착이 발생한다.

이 실패는 락 대기 초과가 아니라 InnoDB가 즉시 검출한 교착이다.
`innodb_lock_wait_timeout`이 50초인데 테스트 전체가 0.131초에 종료됐으므로 대기 초과는 성립하지 않는다.

정상 종료된 6건 기준으로는 쿠폰 수(6)와 재고 차감량(4)이 2건 어긋나,
동시성 제어가 없으면 재고 차감이 유실됨을 확인했다.

반복 측정에서 세 가지 규칙성을 확인했다.

첫째, 성공 응답 수와 락 경합 실패의 합이 항상 정확히 30이다. 전 회차가
6+24, 7+23, 8+22로 떨어졌다. 재고 소진·중복 발급·기타 예외가 전 회차 0건이므로
요청 30건이 빠짐없이 두 갈래로 분류됐고, 테스트 계획 5.4의 합계 검증을 매 회차 만족한다.

둘째, 성공 응답 수와 실제 쿠폰 수가 전 회차 일치했다. 락이 없어도 한 요청 안에서는
트랜잭션이 유지되므로, 응답만 성공하고 쿠폰이 남지 않는 경우는 발생하지 않는다.
NoLock이 잃는 것은 동시 요청에 대한 격리이지 한 요청 안의 원자성이 아니다.

셋째, 초과 발급은 전 회차 0건이다. Level 1 규모(재고 10 / 사용자 30)에서는 경합이
교착으로 먼저 걸러지기 때문에 초기 재고를 넘겨 발급되는 상황까지 가지 않는다.
이 규모에서 NoLock의 실패 양상은 초과 발급이 아니라 차감 유실 쪽이다.

다만 초과 발급이 발생하지 않는 것은 규모가 아니라 **초기 재고 크기** 때문이다(3.1.1 참고).

#### 3.1.1 초과 발급 재현 (재고 2장)

초기 재고를 2장으로 줄이고 API 경로로 동시 요청 60건을 보내면 초과 발급이 재현된다.
`COUPON_STRATEGY=NO_LOCK`으로 애플리케이션을 띄우고 측정한 결과다.

```text
200 ISSUED                 4건   ← 초기 재고(2장)보다 2장 많다
409 OUT_OF_STOCK          43건
503 CONCURRENCY_CONFLICT  13건
500                        0건
합계                      60건

최종 DB: total_stock=2, remaining_stock=0, 쿠폰 4장
```

초과 발급 2건이다. 동일한 실험 환경에서 재고 10장일 때는 교착이 먼저 발생해 초과 발급이
관측되지 않았지만, 재고 2장 조건에서는 재현됐다. 초과 발급은 초기 재고 대비 동시 요청 규모와
트랜잭션 경합 시점의 영향을 함께 받는다.

두 조건은 초기 재고(10장 / 2장)와 동시 요청 수(30건 / 60건)가 함께 달라졌으므로,
어느 한 변수의 기여도를 이 결과만으로 분리할 수 없다. 동시 요청 수·도착 분포,
트랜잭션 실행 시간, DB 스케줄링, 커넥션 풀, 교착 발생 시점이 모두 관여한다.

**재고 카운터는 음수가 되지 않는다.** JPA 더티 체킹이
`UPDATE campaign_stocks SET remaining_stock = ?` 형태로 **절대값**을 쓰기 때문이다.
`remaining_stock - 1`이 아니라 각 트랜잭션이 읽은 값에서 계산한 결과를 그대로 덮어쓰므로,
값이 겹쳐 쓰일 뿐 아래로 넘어가지 않는다. 게다가 코드가 `remainingStock <= 0`에서
`OUT_OF_STOCK`으로 먼저 빠지므로 음수를 쓰려는 시도 자체가 없다.
따라서 스키마의 `ck_stock_nonneg CHECK (remaining_stock >= 0)`는 이 구조에서 도달하지 않는다.

즉 V0의 실패는 "재고가 음수가 된다"가 아니라 **"차감이 유실되면서 쿠폰만 늘어난다"**는
형태로 나타난다. 정합성 위반은 `remaining_stock`이 아니라 쿠폰 수와의 차이로 드러난다.

Level 2(재고 10,000 / 요청 20,000)에서 이 값이 얼마로 나오는지가 V0 가설의 검증 지점이다.

### 3.3 판정

기준선 목적을 달성했다.
테스트 계획 5.4의 NoLock 예외 규정에 따라 정합성 위반은 예상된 결과이며,
별도로 확인하는 항목은 다음과 같다.

- 전체 요청이 제한 시간 안에 종료됐다.
- 처리되지 않은 예외는 0건이다.
- 캠페인별 1인 1매 UNIQUE 제약이 동작했다.
- 요청 30건이 모두 집계됐다(합계 검증 통과).

### 4.1 판정

Level 1 공통 검증 항목을 모두 충족했다.

- 처리되지 않은 예외 0건
- 성공 건수(10) = 초기 재고(10)
- 쿠폰 수(10) = 성공 건수(10)
- 잔여 재고 0장 = 초기 재고 - 성공 건수
- 캠페인별 사용자 중복 발급 0건
- 요청 30건이 모두 집계됨(합계 검증 통과)
- 제한 시간 안에 전체 종료

### 4.2 락 timeout 관련

락 timeout은 0건이다.
모든 트랜잭션이 동일한 재고 행을 `SELECT ... FOR UPDATE`로 먼저 잠그기 때문에
획득 순서가 일정하며 교착이 성립하지 않는다.

현재 `GlobalExceptionHandler`는 `LOCK_TIMEOUT`을 503(SERVICE_UNAVAILABLE)으로 응답한다.
인수 기준이 5xx 0건이므로 Level 2·3에서 락 timeout이 발생하면 그대로 판정 실패로 이어진다.
Level 1 규모(재고 10 / 사용자 30)에서는 0건이지만, 대규모 부하에서의 발생 여부는 별도 확인이 필요하다.


## 5. 종합

| 버전 | 판정 | 비고 |
| --- | --- | --- |
| V0 NoLock | 기준선 목적 달성 | 재고 차감 유실 재현. 교착 24건 관측(5회 범위 22~24). 재고 10장에서는 초과 발급 0건이나 재고 2장 조건에서는 재현됨(3.1.1) |
| V1 비관적 락 | 공통 검증 항목 충족 | 초과 발급 0건, 락 timeout 0건. 5회 전부 동일 |
| V2 Redis Lua | 1-B 담당, 별도 기록 | `CouponConcurrencyTest` 구현됨(`a9da0e2`) |

### 5.1 후속 확인 사항

- 초과 발급은 재고 2장 조건에서 재현됐으나 재고 10장에서는 관측되지 않았다(3.1.1). 초기 재고 대비 동시 요청 규모와 경합 시점이 함께 작용하므로, Level 2(재고 10,000 / 요청 20,000)에서 얼마로 나오는지 별도로 판정한다.
- 요청당 쿼리 2개가 추가되어 Level 2의 TPS 비교 시 run 2 이전 수치와 직접 비교하지 않는다.
- JUnit 동시성 테스트와 API 경로는 경합 강도가 다르다. 같은 조건(재고 10 / 30건)에서 JUnit은 교착 22~24건, API는 2건이었다. Level 1의 교착 건수를 Level 2 예측에 그대로 사용하지 않는다.
